# 更新报告

## 2026-05-13 — Ollama CPU 飙升 / Docker 崩溃 / SSE "连接意外断开" / CORS 500 错误

### 问题 1：SSE 流式对话误报"连接意外断开"（终极修复）

**现象**：发送消息后意图识别显示正常，但最终回复被红色错误 "错误: 连接意外断开，请重新发送消息" 替换。刷新页面后 AI 回复正常显示（说明后端已成功写入数据库）。

**根因**（三层叠加，前两次修复未彻底解决）：

1. **`sse-starlette` 换行符不匹配**：`sse_starlette/sse.py` 中 `DEFAULT_SEPARATOR = "\r\n"`（CRLF），SSE 事件分隔符为 `\r\n\r\n`。前端 `client.ts` 旧代码只检查 `buffer.includes('\n\n')`，永远匹配不到 `\r\n\r\n` → 所有事件被静默跳过。

2. **后端双 `data:` 前缀**：`chat_service.py` 和 `chat.py` 在 `yield` 字符串中硬编码了 `data: ` 前缀和 `\n\n` 后缀。`EventSourceResponse` 又自动为每行添加 `data: ` 前缀 → 实际输出 `data: data: {"type": "done", ...}` → 前端 `JSON.parse(eventStr.slice(6))` 拿到 `data: {...}` 字符串而非有效 JSON → 解析失败 → 静默跳过。

3. **前次修复未真实部署**：`docker cp` 在 Windows 上因路径解析问题（Git Bash 将 `/app/...` 路径映射到 `C:/Program Files/Git/app/...`）静默失败，Python `.pyc` 缓存使容器继续加载旧代码。改用 `cat | docker exec -i` 管道注入并清除缓存后生效。

**修复**：

| 文件 | 修改 |
|------|------|
| `backend/app/services/chat_service.py` | 5 处 `yield`：移除 `f"data: "` 前缀和 `\n\n` 后缀 → 改为 `yield json.dumps({...})`（由 EventSourceResponse 自动格式化） |
| `backend/app/api/v1/chat.py` | done 事件解析从 `event.replace("data: ", "").strip()` → `json.loads(event)`；3 处 `yield` 移除 SSE 前缀后缀 |
| `tauri-app/src/api/client.ts` | 全面重构 SSE 解析器：拆分 `containsEventSeparator()` / `extractNextEvent()` / `extractDataLine()` 辅助函数；同时支持 `\n\n` 和 `\r\n\r\n` 分隔符；处理 `data:` 和 `data: ` 两种格式；添加 `AbortController` 120s 超时控制；区分错误类型（超时/网络/断开）；添加完整 console 调试日志 |

### 问题 2：Docker Ollama CPU 100%+ 导致 Docker Desktop 崩溃

**现象**：Ollama 在对话时 CPU 瞬间飙升至 100%+，Docker Desktop 响应卡死甚至崩溃。Ollama 日志出现 Go panic (`net/http.(*connReader).backgroundRead`)。

**根因**：

1. **模型频繁加载/卸载**：未设置 `OLLAMA_KEEP_ALIVE`，每次对话完成后模型被卸载，下次对话重新加载（~5s CPU 满载）
2. **并发推理过载**：`OLLAMA_NUM_PARALLEL=2` 允许 2 个并发请求，2 个 CPU 核心同时做 CPU 推理导致满载
3. **内存不足触发 OOM**：`memory: 4G` 不足以同时容纳 qwen2.5:1.5b (~3.5GB) + bge-m3 (~1.5GB)，触发 OOM Killer → Go panic

**修复**：

| 参数 | 旧值 | 新值 | 效果 |
|------|------|------|------|
| `deploy.resources.limits.cpus` | `2` | `3` | 推理有余量 |
| `deploy.resources.limits.memory` | `4G` | `6G` | 两个模型同时驻留 |
| `OLLAMA_NUM_PARALLEL` | `2` | `1` | 串行处理，杜绝并发冲顶 |
| `OLLAMA_MAX_LOADED_MODELS` | `1` | `2` | qwen2.5 + bge-m3 同时加载 |
| ✨ `OLLAMA_KEEP_ALIVE` | 未设置 | `-1` | 模型永久驻留，消除加载循环 |
| ✨ `OLLAMA_FLASH_ATTENTION` | 未设置 | `1` | 加速注意力计算 |

### 问题 3：chat/send 返回 500 + CORS 错误

**现象**：对话请求返回 "Failed to fetch" + CORS policy 报错 + 500 Internal Server Error。

**根因**（两个独立问题叠加）：

1. **循环导入**：`chat.py` 中 `from app.main import AsyncSessionLocal` → `main.py` → `router.py` → `chat.py` 循环依赖，模块加载失败 → 端点崩溃 → 500
2. **异常处理器绕过 CORS**：`global_exception_handler` 直接返回 `JSONResponse`，其中间件在异常处理链中排位靠后，500 响应无 CORS 头 → 浏览器拦截

**修复**：

| 文件 | 修改 |
|------|------|
| `backend/app/api/v1/chat.py` | 移除 `from app.main import AsyncSessionLocal`，仅保留 `get_db` |
| `backend/app/main.py` | `global_exception_handler` 显式添加 `Access-Control-Allow-Origin/Methods/Headers: *` 响应头 |

### 问题 4：Ollama 推理超时

**现象**：CPU 推理在 Ollama 繁忙时偶发超时，导致对话生成失败。

**修复**：

| 文件 | 修改 |

### 经验教训

1. **Windows + Docker 文件部署陷阱**：`docker cp` 在 Windows Git Bash 下路径解析不可靠，应改用 `cat | docker exec -i` 管道注入
2. **`.pyc` 缓存隐蔽性**：修改 `.py` 文件后必须清除 `__pycache__/`，否则 Python 持续加载旧字节码
3. **SSE 标准与实现差异**：SSE 规范规定分隔符可为 `\r\n`/`\n`/`\r`，`sse-starlette` 默认使用 `\r\n`，前端解析器必须兼容
4. **`EventSourceResponse` 自动格式化**：向 sse-starlette 的 `EventSourceResponse` 传入的字符串不应包含 `data: ` 前缀，它会在每行自动添加
